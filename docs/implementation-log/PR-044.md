# PR #44 — Add isolated DB2 Auto EAD staging objects

## Scope
- Add a DB2 LUW staging table for schedule-level Auto EAD.
- Add a DB2 procedure parameterized by reporting date that refreshes rows for that date.
- Document execution order, sample invocation, upstream dependencies, and modeling boundaries.
- Keep DB2 source-specific SQL separated from the SQL Server/T-SQL ECL runtime and CI migrations.

## Files
- `database/db2/001_create_auto_ead_schedule.sql`
- `database/db2/002_sp_calc_auto_ead.sql`
- `database/db2/README.md`

## Decisions
- `P_PROCESS_DATE` is the reporting/run date, not the schedule source snapshot's update date.
- `EAD_0` is populated from `FCC_RPTB_CL020.OUTSTANDINGVND`.
- Future schedule rows use `FCC_LOAN_SCHEDULE.AMOUNT_DUE` for `COMPONENT_NAME = 'PRINCIPAL'` and due dates after the reporting date.
- Reruns delete and reload only the requested reporting date.
- This remains upstream staging, not a replacement for the canonical EAD input table used by the SQL Server engine.

## Validation
- Repository structure and `AGENTS.md` reviewed.
- SQL was statically reviewed only; DB2 runtime execution was not available through this workflow.
- No SQL Server CI tests were changed or run because these objects target DB2 and depend on TPB-specific source tables.

## Limitations / follow-up
- Source schedule is currently a latest snapshot and may not represent the schedule as-of the reporting date.
- This initial implementation does not apply settled amounts, readjustments, waivers, write-offs, Auto product filtering, or extra quality rules.
- The output is schedule-level `EAD_AFTER_REPAYMENT`; year-end EAD aggregation and mapping into the canonical EAD input contract are not included.
- Review the DB2 procedure and run it against a non-production DB2 environment before using its output for ECL.
